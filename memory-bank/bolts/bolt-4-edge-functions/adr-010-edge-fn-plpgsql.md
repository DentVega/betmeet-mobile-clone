# ADR-010 — Edge Functions as the write API; plpgsql SECURITY DEFINER for atomicity

- **Status:** Accepted (Bolt 4)
- **Context:** v1 writes need atomic multi-statement DB work (pool+owner-membership, dual prediction upsert, capacity-check+insert) and faithful business rules. supabase-js (Deno) cannot run multi-statement transactions; doing checks then writes in JS risks TOCTOU races.
- **Decision:** Mobile calls **Edge Functions (Deno)** as the write API (`functions.invoke`). Each function verifies the JWT, validates input, maps errors, and delegates the atomic mutation to a **plpgsql `SECURITY DEFINER` function** (`fn_create_pool`, `fn_join_pool`, `fn_join_pool_by_token`, `fn_save_prediction`) that reads `auth.uid()` and runs as one transaction. Token generation (create-pool) and scoring math (compute-score) stay in Deno. `compute-score` is guarded by an `x-admin-secret` header (no user JWT), since v1 result entry is a manual/maintenance op.
- **Alternatives:** all logic in Deno with sequential calls (rejected — not atomic); call the plpgsql functions directly from mobile via `supabase.rpc()` and drop Edge Functions (rejected — user chose an Edge-Function API; but the functions are written so this stays possible); port everything to plpgsql with trivial wrappers (rejected — scoring/token clearer in TS).
- **Consequences:** True transactionality + RLS-bypassing writes confined to audited functions; uniform typed write API; advisory lock in `fn_join_pool*` closes the capacity race. Requires `supabase functions deploy` + `supabase secrets set ADMIN_SECRET=…` (user steps, like `db push`). SECURITY DEFINER functions get `execute` granted to `authenticated`.
